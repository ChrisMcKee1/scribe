# Scribe macOS Porting Plan

## Current baseline

- Status: most of the Windows 0.4.3 feature set is present on macOS; "Parity at a glance" below says, area by
  area, what is present, partial, missing or not applicable. The larger gaps: the default speech model is
  English-only, there is no voice activity detection and no chunked decode of long recordings, AI cleanup has no
  dictionary glossary (with cleanup on, the dictionary's one-line rules correct the transcript the model is sent
  instead) and no GitHub Copilot provider (Windows-only: it shells to the Copilot CLI and its Settings
  panel offers a WinGet install), there is no log file or diagnostics export, and packaging and updates stop at an
  ad-hoc signed app and a manual update check.
- Existing macOS code: `macos/Scribe` SwiftPM menu bar app: full dictation pipeline (hotkey, capture, ASR via
  Foundry Local, AI cleanup, text injection), dictionary, libraries, snippets and app profiles, a Settings window
  with twelve sections (Overlay, Input, Dictionary, Libraries, Snippets, App Profiles, AI Cleanup, Playground,
  Diagnostics, Usage Insights, History, About), and AI cleanup across Foundry Local, managed Ollama, any
  OpenAI-compatible endpoint, and Microsoft Foundry cloud (Azure CLI or service-principal auth, secrets in Keychain)
- Windows now normalizes Foundry project URLs to account `/openai/v1/` inference and reports
  unavailable cleanup through its failure feedback instead of silently skipping it. macOS now routes
  the same way: every saved endpoint shape reaches the account's `/openai/v1/chat/completions` (see
  the "AI cleanup, Microsoft Foundry cloud" row). The failure feedback is ported too: a dictation whose
  cleanup could not start, failed or was rejected goes in exactly as it would with cleanup off, with the pill's own
  "Cleanup failed, raw text used" notice (see the "Dictation lifecycle and pipeline order" row).
- The rows of the detailed checklist further down say how each feature is built and what of it is verified only
  by tests; follow-ups are called out inline per row.

Windows quick-add follow-up: the "Tray quick add to dictionary" row below covers the original flow.
Windows now offers **Save** to refresh the corrected dictation and keep editing, plus **Save and
close**. macOS `QuickAddView.swift` has not yet adopted those separate actions or the refreshed
word-chip and recent-picker state between saves.

Windows 0.4.3 follow-up (2026-09-23): these Windows behavior changes may have made the matching rows
below stale. Nothing under `macos/Scribe` was changed for them unless a bullet says macOS now matches or carries a
**macOS:** note, which describes what has since been ported.

- **Pause passes the push-to-talk key through.** While paused, every new press of the bindings reaches
  other apps and nothing starts a dictation. **macOS:** matches: the event tap is listen-only, so it
  can never hold a key back; while paused, `DictationController` turns the press away and the key's
  listener stays free for the press after resuming.
- **Conditional clipboard restore.** Windows puts the previous clipboard text back only when the
  clipboard still holds exactly what Scribe placed there, so a copy made during a dictation is kept.
  macOS now matches: `PasteboardLease.swift` restores only while the pasteboard `changeCount` still
  equals the one recorded right after Scribe's write (see the "Text injection" row).
- **Adaptive silence auto-stop.** The tracker follows a noise floor and counts a buffer as voice only
  above both an absolute floor (about -45 dBFS) and the floor plus 10 dB, after a short calibration.
  macOS now matches: `SilenceAutoStopTracker.swift` is a port of the Windows tracker, fed the peak of
  every 10 ms of capture timed by sample count (see the "Silence auto-stop for toggle mode" row).
- **Chunk seam planning.** Long captures are split with all seams placed together on the quietest
  audio, and one extra chunk is planned when a capture sits just under a multiple of 30 s.
- **History no longer blocks readiness.** The next dictation is accepted as soon as text is inserted;
  one ordered background writer commits history. **macOS:** `HistoryWriter.swift` queues the entry after
  injection and commits in order off the main actor (at most 16 outstanding; a new entry is dropped and
  logged rather than blocking), and a bounded drain runs at quit. History is best-effort between injection
  and commit: a crash in that window loses the entry, because the tray's recovery ring is memory-only.
  Clear history is a step in the same line, so a successful Clear is never followed by an entry dictated
  before it. The readiness part matches too: a new recording can start while earlier dictations are
  still being processed, and their text goes in in dictation order (`DictationController`).
- **Atomic ASR and VAD load and use.** Loading and using each model is one step under its service's
  gate, so an idle unload can no longer land between them.
- **Decode cancellation.** A long decode stops between chunks at shutdown and never returns a partial
  transcript. macOS has no chunks (Foundry Local transcribes the whole recording in one call), but
  cancelling the transcription stops the recognizer's process group and never returns a partial
  transcript (see the "ASR wrapper" row), and quit does it: `applicationShouldTerminate` answers
  `.terminateLater` and replies only once the recognizer's process group has been stopped and reaped
  (`DictationController.shutDown`).
- **Storage retention and PCM16.** Stored audio is 16-bit PCM with a self-describing header, kept 7
  days and 250 MB at most; cleanup failure samples go after 7 days whatever later cleanups do; the
  newest damaged database copy is kept until the user deletes it. **macOS:** stores no audio, failure
  samples or damaged copies, so only text retention applies: `StorageMaintenance.swift` deletes history
  past the chosen limit 30 s after launch and daily (wall clock), in batches that each re-check the choice
  in their own transaction, so switching to Forever mid-sweep stops it. It then reclaims the space while
  the app is idle: no dictation holds a `ForegroundActivity` lease and nothing has used the database for a
  minute. It uses one conversion VACUUM for an older file, then `incremental_vacuum` steps, and stops the
  moment a dictation starts. Deleted text is written over with zeros as it is deleted (`secure_delete = ON`),
  and every deletion or rewrite of stored text leaves a WAL checkpoint owed, which copies the zeroed pages into
  the database file and truncates the WAL: a history deletion (retention, Clear) and a reclamation owe it in
  the pass that made them, and a dictionary entry, snippet or app profile deleted, or an entry changed (by Quick
  Add, or by an import that updates it), asks for a pass that only checkpoints, through the store's count of
  those writes (`PersistenceStore.removedTextCount`). The old text is gone from both files once the checkpoint
  succeeds; it waits while a dictation runs, is retried with backoff while a reader keeps it busy, and a pass
  that stood aside for a Clear History is asked for again when the Clear ends, whether it succeeded or failed.
  Text deleted by an earlier build can remain in free pages until they are reused or reclaimed.
- **AI cleanup safe reasons and shape-only logging.** Failure and skip reasons are diagnostics-safe
  phrases, the endpoint's own text reaches only Settings, and provider failures are logged by their
  shape, never their message. macOS now matches on the provider side: provider and credential errors
  are typed and carry no response body, `az` output, URL, tenant or client id; they log as their
  `FailureShape`, and the endpoint's own words reach only the Settings status line
  (`CleanupFailureText.forSettings`). The dictation pipeline logs through `ScribeLog` by shape too
  (`DictationController`): ids, counts, durations and enum names, never a transcript, a rule, a profile
  name or the target app, and a test runs the whole pipeline with canaries in every piece of text.
- **Store field policy.** Responses requests always send `store=false`; Chat Completions requests
  never set `store`. macOS matches: every provider sends Chat Completions without a `store` field,
  pinned by wire tests, and there is no Responses route.
- **Silence auto-stop follows the binding that fired.** A held binding never auto-stops, even when the
  other binding is a toggle, and the tracker belongs to its own recording. **macOS:** matches: the
  tracker belongs to its recording's `CaptureProcessor`, and `DictationController` picks the
  `CaptureStopPolicy` from the binding that fired and the user's choice, read at each press. As on Windows,
  where `AutoStopOnSilence` is off by default and `CaptureTriggerBinding.StopsOnSilence` applies it to toggle
  bindings only, Caps Lock (the default key, tapped on and off) stops on silence only when "Also stop after a
  pause" is on in Settings > Input (`HotkeySettingsStore.autoStopOnSilence`, off by default); every other key
  is held and never does; the tray's test dictation always does, so one left running ends by itself; and
  every recording stops at the ten minute ceiling. A toggle whose recording ended some other way (silence,
  the ceiling, a fault, a pause, a rebind) is cancelled, so its next tap is not taken for the second tap of
  that recording (Windows' `CancelToggle`). The event tap only listens and Scribe never synthesizes a lock
  change, so after such an ending, a press Scribe turned away, or a launch with the light on, Caps Lock's light
  is on with nothing recording. A recording starts only when the lock turns on (and ends at its next change),
  so the next tap turns the light off and starts nothing, and the tap after it starts the next recording: the
  light is back in step after one tap.
- **One owner per capture.** A capture opened after its recording ended goes to that recording's
  processing or is reclaimed, so a pause or microphone fault at the start never leaves the microphone
  on. macOS now matches in `AudioCaptureEngine`: every start and stop names its `RecordingID`, a stop
  refuses that recording's start if the device has not opened yet and closes it right after if it
  was opening, and a buffer that arrives after a stop is dropped.
- **Mandatory clipboard receipt.** A paste is confirmed only by state read while the clipboard is held;
  when the receipt cannot be written Scribe types instead. macOS has no pasteboard lock to hold, so its
  equivalent is the `changeCount` recorded right after Scribe's write, read again immediately before
  Command-V and before the restore; when it has moved Scribe types instead and leaves the newer copy.
- **AI switch ordering.** The newest user choice for AI cleanup wins, from the tray or from Settings,
  and a save never overwrites a switch value its window did not show. macOS has no Save: the tray and
  the AI Cleanup tab both store the switch the moment it changes, and an open tab re-reads it after any
  preference write (`CleanupSettingsModel`), so the newest choice is always the one shown and used.
- **Lost settings after a repair.** History text is kept and partial settings writes are refused until
  the user saves Settings. **macOS:** the retention choice lives in `scribe.db` beside the history it
  governs. Only a choice on record deletes anything: a history that predates the setting, or a value
  that is missing or unreadable, keeps every entry. A database this build creates records the 90-day
  default. There is no database repair on macOS, so the refused-writes part has no counterpart.
- **Prompt-only cleanup changes.** Editing the writing style, prompts or dictionary rebuilds the
  cleanup agent in place instead of restarting the provider.
- **Startup failure notice.** A failed start shows a notice and exits instead of staying hidden.
  **macOS:** one non-modal notice (a notification, posted once macOS has answered the notification
  permission request) covers a database or first rule load that failed, missing Input Monitoring and
  missing Accessibility, with an Open System Settings action for the pane that needs a change. Scribe
  keeps running: a storage failure leaves dictation working without the stored rules (`StartupGate`),
  and the event tap is tried again whenever Scribe becomes active or the tray menu opens, so granting
  Input Monitoring may take effect without a relaunch; that is not yet confirmed on a real Mac.

## Parity at a glance

Against the Windows 0.4.3 feature set. **Present**: macOS does what Windows does, in the way the rows below
describe. **Partial**: macOS does less, or differently in a way a user would notice. **Missing**: not built.
**Not applicable**: Windows needs it for a reason macOS does not have, or macOS decided against it. "Present"
means proven by the unit and scenario tests on the CI runners; what the runners cannot reach (permissions, a real
microphone, real apps, real Foundry Local or Ollama inference, rendering) is named per row further down.

| Area | Status | macOS today |
|---|---|---|
| Push-to-talk key, hold and toggle | Present | Caps Lock by default (a toggle, whose recording starts when its light comes on); any other key is held; a listen-only event tap, so keys always reach other apps. |
| Pause | Present | The tray's Pause Dictation; a paused press reaches other apps and starts nothing. |
| Audio capture | Present | One owner per recording, every input channel averaged in, resampled to 16 kHz, device changes end the recording and keep its audio. |
| Silence auto-stop and the duration ceiling | Present | Port of Windows' adaptive tracker. As on Windows it is off by default for a key tapped on and off (Caps Lock), with a switch in Settings > Input; a held key never stops on silence; the tray's test dictation always does; every recording stops at ten minutes. |
| Voice activity detection | Missing | No Silero model: the recognizer receives the whole capture, leading and trailing silence included. |
| Speech recognition model | Partial | Foundry Local's `parakeet-tdt-0.6b-v2`, which is **English only**; Windows' `parakeet-tdt-0.6b-v3-int8` covers about 25 European languages. `SCRIBE_FOUNDRY_ASR_MODEL` selects another Foundry Local model; there is no language picker on either platform. |
| Bundled, offline-from-install recognizer | Partial | The user installs Foundry Local (Homebrew) and the model downloads on first use; Windows ships its model. Dictation then runs offline. |
| Long dictations | Partial | One recognizer call for the whole recording; Windows splits long captures on their quietest audio. |
| Pipeline order (raw ASR, cleanup, guard and dashes, snippets and dictionary, line breaks) | Partial | `DictationController`. With cleanup off, snippets and then the dictionary, as on Windows. With cleanup on, every replacement is decided once on the raw transcript, exactly as cleanup off decides it (`TextPostProcessor.correctVocabulary`): the vocabulary rules' replacements (one line of at most 100 characters, no em or en dash, already in the reply's normal form, which keeps the space before a punctuation mark that begins a word, as in ".NET") are made in the text sent, and the reply is guarded against that text; the snippets' and the template-like replacements (multi-line, longer, with a dash, deletions, or spacing the reply's normalization would change) are held back and made after the reply, each at most once and only where the reply kept the words that set it off (`finishAfterCleanup`). No rule is matched against the model's text, so a model that returns what it was sent gets exactly the cleanup-off text from the rules (a seeded property test checks thousands of random rule sets; the response guard still rewrites any em or en dash in the reply, a dash the transcript held included), and none of those replacements reaches a provider. Windows instead sends the raw transcript with a glossary and runs every rule on the reply, so there a term the model rewrote is corrected again, and a trigger the model wrote itself expands; on macOS neither happens, and a trigger whose words the model rewrote, dropped or repeated is not expanded. The reply's normalization on macOS keeps the space a model writes before ".NET"; Windows' `NormalizeWhitespace` still takes it out (left to the Windows side). A fallback is exactly the cleanup-off result. |
| AI cleanup providers | Partial | Foundry Local, managed Ollama, any OpenAI-compatible endpoint and Microsoft Foundry (Azure CLI or service principal). No GitHub Copilot provider. |
| Dictionary glossary in the cleanup prompt | Missing | Not ported, and an open decision for the maintainer: Windows sends up to 5,000 dictionary terms with every cloud request (80 to a local model), which changes what leaves the Mac. Instead the model is sent the transcript with the vocabulary rules already applied (see "Pipeline order"), and is not told the terms themselves. So the unused-term cleanup's summary leaves out Windows' note that turning terms off frees room in the list its local models are sent. |
| Cleanup requests stored by the provider | Not applicable | There is no Responses route, whose default Windows overrides with `store=false`; Chat Completions requests go without a `store` field, which that API reads as not stored, so there is nothing to override. |
| Test Connection | Present | A real cleanup request through the provider dictation uses, under Windows' deadline and output ceilings. |
| Dictionary, CSV import and export, history-mined suggestions, cleanup of unused entries | Present | |
| Dictionary libraries | Partial | The eleven built-in libraries and custom ones; no library-overlap warnings (`DictionaryLibraryOverlapAnalyzer`). |
| Voice snippets | Present | |
| Per-app profiles (writing style, newline mode) | Present | Matched on the app captured when the recording started. |
| Text injection | Present | Accessibility first, then a pasteboard borrowed only while Scribe owns it, then typing; never delivered to an app that took focus meanwhile. |
| Dictation recovery | Present | The last five transcripts in Recent Dictations, seeded from history at launch, and a notification with Copy Transcript when text did not go in. |
| Tray quick add to dictionary | Partial | The chip picker and a single Save; Windows' Save and Save and close, with refreshed chips between saves, are not ported. |
| Tray toggles (AI cleanup, pause) | Present | |
| Overlay pill | Partial | The nine anchors and every recording, processing and notice state, in-process; no on-screen preview while an anchor is chosen. |
| Out-of-process overlay | Not applicable | Windows needs it to escape a WPF transparency bug that macOS does not have. |
| Playground | Present | Raw recognition, replacement highlights and per-step timings of the last normal dictation. |
| Diagnostics (P50/P95 latency, real-time factor) | Present | |
| Usage insights and the opt-in AI summary | Present | |
| Welcome | Present | |
| About | Partial | Privacy, support, source, star and the data location; no Save diagnostics bundle. |
| Logs | Partial | Shape-only events to the unified log and standard error; no daily log file, session banner or log retention to go with it. |
| History retention and Clear history | Present | Clear also empties Recent Dictations and the Playground's last dictation, and closes an open Quick Add window. |
| Storage maintenance | Present | Retention sweep in batches, reclamation while idle, WAL checkpoints. Deleted text is written over with zeros as it is deleted (`PRAGMA secure_delete = ON` on every read-write connection, beyond the system SQLite's FAST default). After a history deletion (retention, Clear), a reclamation, or a dictionary entry, snippet or app profile deleted or an entry changed, the owed checkpoint copies those pages into the database file and truncates the WAL, and the old text is gone from both once it succeeds (it waits while a dictation runs, is retried while a reader holds it off, and runs again after a Clear History it stood aside for, even one that failed). Text deleted by an earlier build can remain in free pages until reused or reclaimed. |
| Model storage | Not applicable | Windows reclaims models under the Foundry Local directory its SDK registers for Scribe. macOS uses the Foundry Local CLI's cache and Ollama's, which the user installed and other apps share, so Scribe **never deletes shared Foundry Local or Ollama caches**; it removes only what it made, its scratch recordings. |
| Open at Login (Start with Windows) | Present | `SMAppService`, showing what macOS reports; approval needs a signed app on a real Mac. |
| Quit | Present | Waits for a paste in progress, a recognizer and any `az` or `foundry` child before it replies. |
| Updates | Partial | A manual Check for Updates; no automatic updates (Windows: Velopack and the Microsoft Store). |
| Packaging and signing | Partial | An ad-hoc signed app bundle and a disk image; notarization is scripted but has not been run. CI builds the app bundle on every push, lints its Info.plist, verifies its ad-hoc signature and runs its library listing from inside the bundle. |
| Processor architectures | Partial | Apple Silicon only; Windows ships x64 and Arm64. |
| NPU and GPU selection for cleanup | Not applicable | Foundry Local's service chooses the execution provider, as its SDK does on Windows. |
| Scenario suite on the speech fixtures | Partial | `ScribeScenarioTests` runs the committed fixtures headlessly through capture, silence, the pipeline and storage with a stand-in recognizer; the real recognizer runs only in the optional, hand-dispatched workflow job, which fits a hosted runner, on the clean short fixtures, without Windows' long-audio, channel-mix and degraded-audio sweeps. |

## Feature parity checklist

| Feature | Status | Owner | macOS implementation approach |
|---|---|---|---|
| Overlay pill with 9-anchor position picker | Done | Frontend | `OverlayPanelController` (`OverlayPanel.swift`): borderless, non-activating `NSPanel` hosting a SwiftUI `OverlayPillView`; `OverlayAnchor.swift` computes the 9-position origin from `NSScreen.visibleFrame`. Position picked from a status-bar submenu (its checkmarks re-read when the tray menu opens, so a choice made in Settings shows there) and a Settings grid picker, persisted via `UserDefaults` (stopgap; a general Settings preferences store doesn't exist yet). The panel joins every space including a full-screen app's (`.fullScreenAuxiliary`); whether it appears over a full-screen app needs a real Mac to confirm. |
| Overlay live recording state and meter | Done | Frontend | `DictationSessionModel` (ObservableObject) drives `OverlayPillView` through `hidden`/`listening(levelDbfs:)`/`processing`/`notice(OverlayNotice)`, the last split by stage so a label always names what failed: "Cleanup failed, raw text used", "Microphone unavailable", "Speech recognizer not found", "Transcription failed", "Not inserted, text kept", "Only partly inserted" and a few more (`OverlayAnchor.swift`). Every change comes from `DictationController` with the next revision (`DictationPresentation`), and the pill renders a change only when its revision is newer than the last one shown, so a late, older change can never undo a newer one (Windows' `PresentationRelay`). Outcomes go through one schedule (`DictationNoticeSchedule`): one notice at a time, for its whole time; a recording owns the pill from its admission, so an outcome that arrives meanwhile waits for the recording to end rather than being lost; a notice on the pill is never replaced by an outcome that arrived after it, so an older dictation's late fallback cannot take down a newer microphone failure; a cleanup fallback or a failed recognition the pill cannot show at once is posted as a notification instead; duplicates, outcomes after shutdown began and outcomes about text Clear history removed are dropped. A notice's timed end is tagged with the revision that showed it, so a stale end changes nothing, and the old "late hide takes down the next recording's pill" cannot happen. The meter comes from the capture engine's level events, at most one per buffer and one per 50 ms of audio, which `CaptureEventRelay` brings to the main actor with at most one delivery waiting (the newest reading wins), and a reading from a recording that no longer holds the microphone is dropped. In-process (no separate overlay process/IPC needed on macOS since there's no WPF transparent-window bug to work around). Rendering itself needs a real Mac. |
| Settings navigation replacing static stub | Done | Frontend | `SettingsView.swift`: a `NavigationSplitView` sidebar with twelve sections (Overlay, Input, Dictionary, Libraries, Snippets, App Profiles, AI Cleanup, Playground, Diagnostics, Usage Insights, History, About), since a segmented `TabView` does not fit a dozen; the tabs that edit rules and history go through models over `PersistenceStore`'s asynchronous calls, so none waits on the database on the main thread. Replaces the earlier one-paragraph static text scaffold. `PersistenceStore` gained `fetchAll*`/`set*Enabled`/`delete*` methods and a `databaseURL` override initializer for testability; covered by 9 new `PersistenceStoreCRUDTests`. |
| User dictionary, core substitution | Done | Backend | `TextPostProcessor` applies whole-word, case-insensitive dictionary substitutions from a new SQLite `dictionary_entries` table, matching Windows' single-pass, longest-match-first semantics. Rules are compiled once per reload, as Windows' `CompiledRule` is, rather than for every dictation, off the main actor (`DictationRuleSnapshot.compile`: about 20 to 30 ms with every built-in library and twenty snippets on the CI runners, where the previous matcher's compile took 150 to 210 ms), and installed in one step, so a dictation meets either the old rules or the new ones; a supplementary character (an emoji) right before a punctuation rule no longer traps. Unit-tested. `Scribe --post-process-text` runs the same processor over the user's enabled rules and snippets, read through a read-only store (`PersistenceAccess.readOnly`), and when there are neither it runs fixtures in a temporary database of its own, so the verb never changes the user's database (a read-only connection may still create SQLite's `-wal` and `-shm` files beside it). CSV import/export and history-mined suggestions remain separate follow-ups below. |
| Dictionary CSV import/export | Done | Platform | `DictionaryCsv.swift` and `DictionaryImportMerger.swift` are line-for-line Swift ports of `Scribe.Core.PostProcessing.DictionaryCsv` / `Scribe.Core.Settings.DictionaryImportMerger`, including the exact error wording, RFC 4180 quoting rules, and the case-insensitive "first writer wins, update or add" merge semantics. `DictionarySettingsTab` gained Import CSV/Export CSV/Get Template buttons backed by `NSOpenPanel`/`NSSavePanel`. 17 new XCTests port the C# xUnit suite 1:1 (round-trip, quoting, comments/header skipping, bad-row line numbers, merge add/update/unchanged/dedup). Found and fixed a real porting bug this way: a naive `Character`-based CSV reader silently drops every record after the first because Swift's grapheme clustering merges `"\r\n"` into one `Character`, defeating a `case "\n":` switch arm that assumed C#'s per-UTF-16-char semantics; fixed by iterating `unicodeScalars` instead. Live-verified the Get-Template -> Import round trip via the real Settings window (`NSSavePanel` save confirmed byte-identical template content on disk); `NSOpenPanel` proved too flaky to drive end-to-end via AppleScript in this sandbox, so the import path is trusted on its unit tests plus the identical, already-verified `NSSavePanel` pattern. The import reads the stored rules, applies the merge plan to them (`DictionaryImportMerger.changes(applying:to:)`) and writes the result in one `BEGIN IMMEDIATE` transaction (`PersistenceStore.importDictionary`), so it never plans against rows the Settings tab has not loaded yet or that an earlier import has just changed, a spoken form imported twice in one file is stored once with its later value, and a failure part way leaves the dictionary unchanged; the tests assert the stored rows, including an import made while the first load is held behind a write and one made while an earlier import is still refreshing. |
| Dictionary history-mined suggestions | Done | Backend | `DictionarySuggestionMiner.swift`, `DictionaryTermVariants.swift`, and `DictionaryHistoryLearner.swift` are faithful Swift ports of `Scribe.Core.PostProcessing.DictionarySuggestionMiner` / `DictionaryTermVariants` / `DictionaryHistoryLearner`: mine recurring "jargon-shaped" tokens (acronyms, CamelCase humps, letter+digit like K8s) across distinct dictations, then derive only the two safe/recoverable pattern shapes (acronym letter-spelling, 3+ letters; CamelCase compound-splitting filtered against a common-words stoplist) rather than inventing an unobserved `lowercase -> term` rule. Required a schema change: `dictation_history` gained a `transcript_text` column (via the existing probe-then-`ALTER TABLE` migration pattern) since the prior schema stored only timing/duration metadata and had no transcript text for the miner to read, unlike Windows' `HistoryEntry.Text`. The live pipeline (`DictationController`) records the final text of each dictation alongside its history row. Surfaced via a "Learn from History" button in `DictionarySettingsTab` (Windows uses a tray menu item instead; a Settings button was chosen for macOS to keep all dictionary actions in one place, reusing the existing `statusMessage` pattern). 20 new XCTests port both C# xUnit suites 1:1. Live-verified end to end via the real app: seeded `dictation_history` rows with a recurring term ("ReBAC" x3), clicked "Learn from History" through AppleScript, confirmed the exact expected pattern/replacement (`re bac` -> `ReBAC`) was inserted into `dictionary_entries`, and confirmed a second click reports "No new recurring terms" (idempotent, no duplicate). |
| Voice snippets | Done | Backend | `Snippet`/`snippets` SQLite table plus `TextPostProcessor` expand spoken trigger phrases into (possibly multi-line) templates before dictionary canonicalization runs, matching Windows' snippets-first ordering. Snippets run after AI cleanup, as on Windows, so a template never reaches a cleanup provider (it would otherwise send the user's saved addresses and signatures to a cloud model) and the model cannot rewrite it; so does any template-like dictionary replacement: one of more than one line, longer than 100 characters, with an em or en dash (so the reply's dash normalization never reaches the user's own dash), a deletion, or one with spacing the reply's normalization would change (`TextPostProcessor.isVocabulary`). With cleanup on, each snippet is decided on the spoken transcript as cleanup off decides it, and made after the reply only where the reply kept its trigger's words, so a trigger is never taken from what a rule or the model wrote. `Scribe --post-process-text` expands the user's snippets the same way, read-only, or a multi-line fixture snippet in a temporary database when the user has no rules or snippets. |
| Per-app profiles by focused app | Done | Platform | `AppProfile`/`AppProfileMatcher` in `AppProfile.swift`; keys on bundle identifier first, process name as fallback, matched against the app that had focus when the recording started (captured with `TextInjector.captureTarget()`), so switching apps while a dictation is processed changes neither the profile nor where the text goes. The profiles are taken as they stood at activation when the rules had loaded by then. SQLite-backed (`app_profiles` table). `Scribe --resolve-profile <bundle-identifier> <text>` matches against the user's profiles read-only, or against fixture profiles in a temporary database when there are none. |
| Per-app writing style override | Done | Platform | `AppProfile.writingStylePrompt` resolved from the captured target and threaded into the dictation's AI cleanup request as the provider's system prompt, falling back to `CleanupPrompt.defaultWritingStyle` when no profile matches or no override is set. When the target flattens line breaks (a terminal), Windows' single-line contract is added to the style (`CleanupPrompt.writingStyle(profileStyle:requireSingleLine:)`, `singleLineWritingStyle`), so the model writes one line rather than paragraphs that are run together afterwards. |
| Per-app newline mode | Done | Platform | `NewlineInjectionMode` (smartFlatten/alwaysFlatten/keepNewlines) mirrors Windows; SmartFlatten checks bundle identifier against a known-terminal list (Terminal, iTerm2, Warp, WezTerm, kitty, Hyper, Ghostty). ## ASR strategy decision

### Correction (2026-08-24)

An earlier pass of this plan claimed Foundry Local "does not have a direct macOS counterpart." That
was wrong: Foundry Local ships a real macOS build via
[`microsoft/homebrew-foundrylocal`](https://github.com/microsoft/homebrew-foundrylocal), verified on
this machine (`brew tap microsoft/foundrylocal && brew install foundrylocal`, v0.10.3, Apple M5 GPU
detected via `WebGpuExecutionProvider`). It also hosts `parakeet-tdt-0.6b-v2` in its model catalog as
a native `foundry transcribe` target, which changes the ASR decision below.

### Decision

**Primary path: Foundry Local's `parakeet-tdt-0.6b-v2` via `foundry transcribe`, not a hand-rolled
sherpa-onnx C bridge.** Keep the shipped Parakeet TDT model family as the ASR path (unchanged from
the original decision), but obtain it through Microsoft's own supported runtime instead of manually
wrapping the sherpa-onnx C API in a thin Swift module.

Verified directly on this machine:

```text
$ time foundry transcribe -m parakeet-tdt-0.6b-v2 -f /tmp/verify_test.wav -o json
{"model":"parakeet-tdt-0.6b-v2-generic-cpu:1","file":"/tmp/verify_test.wav",
 "text":" The quarterly report is due on Friday.","language":null,"durationSeconds":null}
real  1m6.425s   # includes first-run model download + load; steady-state calls are not this slow
```

The transcript exactly matches the same synthesized fixture ("The quarterly report is due on
Friday.") independently verified through `whisper-cli` earlier in this port, so this is a real,
working ASR path today, not a hypothetical.

### Why this beats both alternatives

1. **Parity beats novelty here.** Windows already ships Parakeet TDT, Silero VAD, and no language
   picker. Reusing the same model family keeps the transcript shape and the existing post-processing
   assumptions. It does not keep Windows' language coverage: the default `parakeet-tdt-0.6b-v2` is
   English-only, while Windows' `parakeet-tdt-0.6b-v3-int8` covers about 25 European languages, so a
   non-English dictation that works on Windows does not work on macOS today.
2. **Foundry Local beats a hand-rolled sherpa-onnx bridge for delivery speed and hardware ownership.**
   A native sherpa-onnx C API wrapper means owning: model distribution, ORT session lifecycle, VAD
   segmentation glue, and hardware-provider selection ourselves in Swift. Foundry Local already does
   all of this (it is a real ORT-based runtime with its own model manager and execution-provider
   negotiation), so `foundry transcribe -f <path>` is functionally the sherpa-onnx wrapper we planned
   to build, already built, already shipping on macOS, and already exercising the same execution
   provider selection logic AGENTS.md documents for Windows ("the SDK owns hardware selection, do not
   try to take it back").
3. **Whisper.cpp still changes the product contract**, unchanged reasoning from the original decision:
   Whisper-based integrations push toward a language hint or auto-detect UX, and AGENTS.md is explicit
   that Scribe should not grow a language picker for the shipped model behavior. Parakeet via Foundry
   Local has no such parameter, matching Windows' lack of a language picker (though not its language
   coverage; see point 1).
4. **One runtime, two features.** Foundry Local is already the recommended default for AI cleanup (see
   below), so using it for ASR too means macOS Scribe depends on one Microsoft-supported local
   inference stack instead of three unrelated ones (sherpa-onnx, whisper.cpp, Ollama).
5. **Benchmark comparability still holds.** Keeping the ASR family aligned means Windows and macOS
   cleanup benchmarks stay comparable, because the cleanup model sees similar raw transcript failure
   modes either way.

### Implementation note

- Invoke Foundry Local's `transcribe` subprocess (or its `/v1` HTTP surface, if speech transcription
  is exposed there in a future CLI version; not yet confirmed) from `TranscriptionEngine.swift`
  instead of `whisper-cli`. Treat this as a provider swap behind the existing transcription interface,
  not a rewrite of the capture pipeline.
- `parakeet-tdt-0.6b-v2` is not byte-identical to Windows' `parakeet-tdt-0.6b-v3-int8` (different
  minor version, not yet confirmed int8-quantized on macOS), so re-run the accuracy/latency
  characterization Windows did in `tools/Scribe.AsrCheck` (long-audio, channel-mix, degraded-audio
  sweeps) before treating macOS ASR quality as proven equivalent to Windows. The headless half of that
  harness exists (`ScribeScenarioTests`); the optional real speech recognition job of the macOS workflow
  runs the clean short fixtures through the real recognizer and is the place to add those sweeps.
- Keep `whisper.cpp` as a documented fallback path only, in case Foundry Local's transcription
  latency proves unacceptable for real-time push-to-talk once profiled with longer dictations; it is
  no longer the primary spike target.
- Preserve the no-language-picker product rule. Leaving Foundry Local's optional `--language` flag on
  `transcribe` unset is correct because there is nothing to set: `parakeet-tdt-0.6b-v2` is an
  English-only model with no language parameter. That is also why it does not match Windows v3's
  multilingual coverage; offering other languages on macOS needs a different model, which is a
  separate decision.

## AI cleanup provider architecture

### Provider protocol

```swift
protocol CleanupProvider {
    var id: String { get }
    var displayName: String { get }
    var capabilities: CleanupProviderCapabilities { get }

    func validateConfiguration() async throws
    func warmUp() async throws
    func clean(_ request: CleanupRequest) async throws -> CleanupResponse
    func healthSnapshot() async -> CleanupHealthSnapshot
}
```

Supporting types to plan now:

- `CleanupRequest`: transcript, effective writing style, prompt variant, glossary, timeout, and metadata such as single-line mode
- `CleanupResponse`: cleaned text, latency, token counts if available, and provider-specific diagnostics
- `CleanupProviderCapabilities`: local vs cloud, streaming support, auth modes, managed-runtime support

### Planned concrete implementations

1. `OpenAICompatibleCleanupProvider`
   - Covers LM Studio, OpenRouter, and any other compatible local or remote server.
   - Uses `URLSession` with configurable base URL, model, and API key.
   - This is the portability layer that keeps macOS aligned with Windows' bring-your-own endpoint story.

2. `MicrosoftFoundryCleanupProvider`
   - Reuses the REST API rather than any Windows-only SDK.
   - Supports two auth sources: serialized Azure CLI token acquisition and service principal credentials.
   - Secrets live in Keychain, not plist files or environment variables.

3. `FoundryLocalCleanupProvider`
   - **Recommended default local provider** (see benchmark results in `CLEANUP-MODEL-BENCHMARK.md`).
   - Talks to Foundry Local's real macOS build (`microsoft/homebrew-foundrylocal`) over its
     OpenAI-compatible `/v1/chat/completions` endpoint; port is dynamic, read from `foundry status`
     or the CLI's own reported startup line, not hardcoded like Ollama's 11434.
   - Owns model load/download orchestration via `foundry model load <alias>` (or the equivalent SDK
     call if/when a native Swift or C SDK binding is adopted instead of shelling out to the CLI).
   - Uses the SDK's own hardware selection; Scribe never picks the execution provider, matching the
     "SDK owns hardware selection" rule already established for Windows in AGENTS.md.
   - Same runtime also serves ASR (`parakeet-tdt-0.6b-v2` via `foundry transcribe`), so this provider
     and the ASR wrapper share one install/health-check story instead of two.

4. `ManagedOllamaCleanupProvider`
   - Fully supported alternative local provider, not deprecated by the addition of Foundry Local.
   - Owns health checks, optional install guidance, daemon startup, and curated local-model management, then talks to the same OpenAI-compatible local endpoint (`http://127.0.0.1:11434`).
   - Appropriate for users who already run Ollama for other tools or prefer its model catalog; Settings should let users choose either managed local provider, with Foundry Local pre-selected by default.

### Native on-device choice

**Recommendation: Foundry Local is the default managed local runtime for the first parity release.
Managed Ollama remains a fully supported alternative. MLX-swift in-process inference stays a future
spike.**

#### Foundry Local wins the default slot because

- It is Microsoft's own on-device SDK, the same family Windows Scribe already depends on
  (`Microsoft.AI.Foundry.Local.WinML`), so macOS and Windows share one real architecture for local AI
  instead of two unrelated stacks.
- It owns hardware selection for us (verified: Apple M5 GPU auto-selected via
  `WebGpuExecutionProvider` in this session), the same operating philosophy Windows already follows.
- It serves both AI features macOS needs: chat-style cleanup and Parakeet-family ASR, from one
  install and one health-check surface (see ASR strategy decision above).
- Benchmarked quality is competitive with Ollama at the same parameter count (`qwen2.5-1.5b`: 0.575
  Foundry Local vs. 0.562 Ollama) with a flatter, spike-free latency curve in this run. See
  `CLEANUP-MODEL-BENCHMARK.md` for full numbers.
- This is a deliberate storage/install tradeoff, made on purpose: Scribe's design goal is the best
  local-first experience, even if that costs a second background service and roughly 1.5-5 GB of
  model weights depending on the tier a user selects. Ollama users are not worse off; they simply
  point Scribe at their existing install instead.

#### Managed Ollama stays fully supported because

- Some users already have it installed and configured for other tools, or prefer its GGUF
  quantization ecosystem.
- It already matches the same OpenAI-compatible abstraction, so supporting both providers costs one
  extra `CleanupProvider` implementation, not a second protocol.
- `qwen2.5:3b` on Ollama scored the single best result on that runtime (0.632) and remains a
  legitimate user choice for those who prefer it over Foundry Local's `qwen2.5-1.5b`.

#### MLX-swift stays a future spike because

- It would be truly in-process and dependency-light once weights are installed.
- It would also force us to own model conversion, distribution, and a separate evaluation matrix for MLX-native checkpoints.
- It would add a third local ecosystem alongside Foundry Local and Ollama with no benchmarked quality
  advantage demonstrated yet.

## Provider naming in the macOS UI

Unlike an earlier draft of this plan, `Foundry Local` **is** a real, correctly-named macOS concept
and should be surfaced as such. The Settings provider picker should use:

- `Foundry Local` (default, recommended)
- `Local model (Ollama managed)`
- `Microsoft Foundry` (cloud)
- `OpenAI-compatible endpoint`

In docs, explain that Foundry Local and managed Ollama are both fully local, no audio or transcript
data leaves the device with either, and Foundry Local is recommended by default because it shares a
runtime with the macOS ASR path and matches the Windows architecture most closely.
